DocuSign integration work

🔒 Client names are hidden intentionally: this is my ongoing work at BARS, a DocuSign partner. The code stays private; here I describe the problem, my role, the architecture and the key decisions.

Enterprise client · ongoing

SAP document data for DocuSign Maestro

Need
Before a document is signed, a Maestro workflow must pull the right document data from SAP — but users only know an internal request (RDA) number.
My role
Built a private DocuSign Data IO Extension App in Node.js/Express that Maestro calls server-to-server. It queries SAP over SOAP and returns the document ID, title and status to the workflow.
Flow
Maestro web form→, then Data IO extension (OAuth 2.0)→, then SAP (SOAP)→, then document data→, then signature step
Key decision
OAuth 2.0 client credentials keep the extension a pure server-to-server service with no user login; a tunnel made the full SAP round-trip testable during development.
Status
Working prototype · ongoing
  • DocuSign Maestro
  • Data IO Extension
  • Node.js
  • Express
  • OAuth 2.0
  • SOAP
  • SAP

Enterprise client · proof of concept

SharePoint purchase orders → DocuSign

Need
Vendors must sign a purchase order together with every supporting document stored in SharePoint, sent as a single envelope.
My role
Built a Java/Spring Boot service: from a PO number and revision it finds the SharePoint folder via Microsoft Graph, collects the PDFs, assembles the DocuSign envelope (main PO first) and sends it, returning envelope ID, status and warnings.
Flow
PO request (REST)→, then Spring Boot→, then Microsoft Graph / SharePoint→, then envelope assembly→, then DocuSign→, then vendor
Key decision
A mock mode runs the whole flow without Microsoft or DocuSign credentials, and the REST contract is designed for SAP to call later — so it can be demonstrated and tested before access to client systems exists.
Status
Proof of concept
  • Java
  • Spring Boot
  • Microsoft Graph
  • SharePoint
  • DocuSign eSignature API
  • REST
  • Docker
Public test version (mock mode) → github.com/Tridrik-Dey/sharepoint-docusign-poc

Enterprise client · proof of concept

Signer data from Microsoft Entra ID

Need
Signed documents must carry company and HR attributes of the sender and the employee, ready for archiving in a document-management system.
My role
Built a TypeScript service that resolves envelope roles, matches users by email in Microsoft Entra ID via Microsoft Graph, and writes the mapped attributes as envelope custom fields.
Flow
DocuSign envelope→, then roles→, then email→, then Microsoft Graph /users→, then mapped attributes→, then envelope custom fields
Key decision
Which roles and attributes are used lives in a mapping file, so the business can change it without a code change.
Status
Proof of concept
  • TypeScript
  • Node.js
  • Microsoft Graph
  • Entra ID
  • DocuSign eSignature API
  • Vitest

Italian enterprise client · ongoing

HR e-signature and archiving to Zucchetti

Need
HR onboarding documents should be signed in person on a tablet and then filed automatically in each employee’s folder in Zucchetti HR.
My role
Wrote the bilingual functional analysis (EN/IT) and built the phase-1 prototype: in-person signing, archiving and an action log, on mock data.
Flow
HR on tablet→, then in-person signature→, then signed documents→, then Zucchetti HR (employee folder)→, then action log
Key decision
DocuSign and Zucchetti sit behind adapters, so the real integrations replace the mocks without changing the UI or the business rules.
Status
Analysis + phase-1 prototype · ongoing
